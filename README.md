# 分数最优推进（Android 可用）

一个纯前端 App：输入关卡目标分和每波获得的分数，算出**总溢出最小**的推进方案。

## 玩法模型（App 内置的规则）

- 关卡**按顺序**通关，每关有目标分 `T1, T2, … Tn`（一般 10~15 关）。
- 每波会拿到**若干分数**，可以**自由组合**分配给各关，**整波必须全部用完**才会发下一波。
- 某一关累计到 `≥ 目标分` 即通关，**超出目标分的部分记为「溢出」**（浪费掉，不能带到下一关）。
- 没用完的分数会**留在当前关继续累计**（算进度，不算溢出）。
- 目标：**让整局的总溢出最小**。

> 因为「溢出 = 拿到的总分 − 已通关目标分之和 − 当前关进度」，所以最小溢出 ⟺ 在能通关的前提下尽量多通关、并把分数尽量留在当前关做进度。这两件事不冲突，App 直接对它们做全局最优。

## 内置关卡场景（点选即用）

「关卡设置 → 关卡场景」内置三个场景，点一下自动套用整份关卡表：

| 场景 | 关卡数 | 各关目标分 |
|---|---|---|
| 汉堡叠叠乐 | 15 | 30 50 70 60 80 60 90 110 70 90 110 80 100 130 150 |
| 小鹅拳击手 | 15 | 50 50 60 60 80 80 80 100 100 120 150 150 180 180 200 |
| 金牌外卖员 | 10 | 20 25 35 25 35 45 25 35 45 55 |

切换场景会替换关卡表并**重置进度**（有进度时会先弹确认）。手改或粘贴过目标分后，
场景行会显示「自定义」高亮，表示当前关卡表不等于任何预设。

## 从中间关卡接手

「当前状态 → 调整起始进度」可以直接指定**从第几关开始**和**该关已完成多少分**，
不必从第 1 关 0 分开始。应用后会清空累计溢出与历史记录，从该起点重新统计。

校验：已完成分数必须**小于**该关目标分（填到等于就已通关，应该填下一关）；关卡序号需在 1~总关数之间。

## 怎么用到安卓手机上

三种方式，按方便程度排序：

### 方式 1：局域网起服务（推荐，立刻可用）

电脑上（需要 Node.js）：

```bash
node serve.js
```

会打印出 `http://<电脑IP>:8080`。手机连**同一个 WiFi**，用 Chrome 打开这个地址。
然后 Chrome 右上角菜单 → **添加到主屏幕**，桌面上就会多一个图标，点开即用。

### 方式 2：直接把文件传到手机

把 `index.html` 单独一个文件（它已经把样式和逻辑全部内联，**无任何外部依赖**）通过微信文件传输助手 / 数据线传到手机，
用 Chrome 打开该文件即可。断网也能用。

### 方式 3：GitHub Pages（HTTPS，可安装成 PWA）

仓库推送到 GitHub 后，由 GitHub Pages 提供公网访问（见仓库 Settings → Pages，或使用本仓库自带的
`.github/workflows/pages.yml` 自动部署）。

访问地址一般为：**`https://<你的 GitHub 用户名>.github.io/score-planner/`**

手机 Chrome 打开后会提示**「安装应用」**，装完是独立图标、全屏运行、离线可用（`sw.js` 做了离线缓存）。

### 方式 4：其它静态托管

也可部署到 Vercel / Netlify 等任意 HTTPS 静态站点，效果同方式 3。

> 说明：Chrome 的「安装应用」要求 HTTPS 或 localhost。走方式 1/2 时只会生成普通快捷方式，功能完全一样。

## 使用步骤

1. **选场景**：在「关卡设置 → 关卡场景」点一个内置场景；也可以用「关卡数 + 批量粘贴」自己填。
2. **定起点**：默认从第 1 关 0 分开始；中途接手时在「当前状态 → 调整起始进度」填起始关卡与该关已完成分数。
3. **本波分数**：把这一波拿到的分数逐个输入或整段粘贴，回车加入。
4. 点底部 **计算最优方案** → 看到每关用哪几个分数、各关溢出、剩余进度、本波总溢出。
5. 点 **应用方案** → 进度自动推进到下一关，本波分数清空，累计溢出累加。发下一波后重复第 3 步。
6. 填错了可以 **撤销上一波**；关卡目标分随时可改（已通关的关卡会变灰）。

数据存在浏览器 localStorage 里，关掉再打开还在。

## 算法

**精确解（本波分数 ≤ 18 个）**：位掩码 DP。

状态 `dp[mask]` = 用完 `mask` 里这些分数后能拿到的 `(已通关数 j, 累计溢出 ov)` 最优值。
当前关已累计量可由状态唯一推出：`acc = carry + sum(mask) − 前 j 关目标之和 − ov`。
每加入一个分数就放到当前关，一旦 `acc ≥ 目标` 即通关、超出部分计为溢出、进度归零。
由于分数可以任意顺序投入，DP 天然覆盖了「哪几个分数给哪一关」的所有划分。

复杂度 `O(2^k · k)`，`k ≤ 18` 时约 470 万次运算，手机上半秒内出结果。

**近似解（分数 > 18 个）**：逐关做「最小覆盖」子集和（`target + 最大分数` 容量内做 0/1 背包），
结果会标注「近似解」。

**为什么最大化通关数一定优于少通关**：设通关到第 `j` 关，`有用的分数 = Σ(前 j 关目标) + 当前关进度`。
若放弃第 `j` 关，当前关进度必然 `< Tj`，而通关第 `j` 关直接多拿 `Tj`，恒优于放弃。
所以「先多通关、再把分数留在当前关」就是全局最优，不存在需要跨波次前瞻的取舍。

## 验证

```bash
node test/verify.js
```

把 `index.html` 内联的求解器抽出来，与**独立实现的暴力枚举**（枚举每个分数分配给哪一关）逐例对拍：
5504 个随机用例（含目标分非单调、进度带 carry、分数可超出剩余关卡等边界），结果全部一致。
